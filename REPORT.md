# Ассистент сервисной службы «ПолярТех»

> GitHub-репозиторий команды — [добавить ссылку перед сдачей]

## 1. Задача

Диспетчер сервисной службы получает модель холодильного оборудования и код ошибки. По руководству он определяет неисправный узел и номер детали, а по сервисному бюллетеню проверяет, есть ли у детали замена. Остаток на складе и актуальную цену он узнаёт в ERP. Ассистент должен собрать эти сведения, указать документы-источники и передать оформление заказа на подтверждение диспетчеру.

На вопрос `dev-06` «Какую деталь заказать при ошибке E-17 на AR-210?» плоский RAG ответил: «При ошибке E-17 на AR-210 необходимо заказать деталь P-1042 — пусковое реле». Поиск вернул фрагменты трёх руководств (`manual_AR-210.md`, `manual_AR-310.md` и `manual_AR-220.md`). В них ассистент нашёл исходную деталь, но в контекст не попал [сервисный бюллетень SB-2025-03](data/corpus/bulletin_SB-2025-03.md). Бюллетень сообщает, что P-1042 снята с производства и новые заказы оформляются на P-1042B. Оценщик засчитал ответ как неверный.

## 2. Решение

Для сравнения использован готовый плоский RAG (`baseline`). Модель `bge-m3` строит эмбеддинги вопроса и фрагментов документов. По векторному сходству система выбирает четыре фрагмента, а `qwen3:4b-instruct-2507-q4_K_M` формулирует ответ по ним.

### Извлечение сущностей и связей

Первая реализация FR-1 находилась в отдельном репозитории `final-project`. В доработанной версии из `labs/final-project` промпт явно задаёт направление связей через поля `subject` и `object`, объясняет их смысл и показывает пример полного JSON. Модель также получает словарь названий. Лимит ответа увеличен с 1024 до 2048 токенов, а при повторном запросе добавляется инструкция о формате. Это позволяет получить новый ответ вместо повторного чтения того же результата из кеша.

Функция `extract_chunk` передаёт Qwen3 один фрагмент документа, словарь названий и описание допустимых связей с их направлениями. Модель возвращает два массива JSON: сущности и связи. Pydantic проверяет структуру ответа. Если JSON не разбирается, функция повторяет запрос с уточнением формата. После второй неудачи она возвращает пустой результат с идентификаторами документа и фрагмента.

Затем код приводит коды и названия к каноническому виду, проверяет наличие кодов в тексте и сверяет названия со словарём. Связь сохраняется, если упорядоченная пара типов её концов соответствует схеме и оба конца прошли проверку. Если модель упомянула словарное название только внутри связи, функция добавляет сущность при наличии этого названия в тексте. В ответе по бюллетеню модель записала исходную деталь как `P--1042`. После исправления повторного дефиса и проверки кода по тексту в граф попала связь `P-1042 → REPLACED_BY → P-1042B` с источником `bulletin_SB-2025-03.md#0`. Для `REPLACED_BY` оба конца имеют тип `Part`, поэтому проверка типов сама по себе не отличает старую деталь от новой.

### Построение графа знаний

`build_graph` объединяет результаты извлечения в направленный граф NetworkX. Одинаковые сущности объединяются по идентификатору вида `Part:P-1042`. Каждый узел хранит тип, имя и список фрагментов, в которых он найден. Ребро добавляется после проверки схемы и наличия обоих узлов. Вес ребра равен числу уникальных фрагментов-источников, поэтому повтор связи внутри одного фрагмента не увеличивает вес.

Если две детали указывают друг на друга через `REPLACED_BY`, граф сохраняет направление с большим весом. При равных весах обе связи удаляются. Каждая встречная пара учитывается один раз в счётчике конфликтов.

### Сообщества и поиск

Для выделения сообществ алгоритм Лувена получает ненаправленную копию графа с весами рёбер и фиксированным начальным значением генератора. Сам граф сохраняет направления связей. Число отказов подсчитывается в Python по весам рёбер `FAILED` для каждой линейки и узла. Каждый отказ учитывается в сообществе узла оборудования. Qwen3 получает факты и подсчёты и формирует сводку до 150 слов.

В режиме `local` коды и словарные названия из вопроса служат опорными узлами. Для нескольких опор поиск собирает пути длиной до трёх рёбер между ними и продолжает цепочки замен от найденных деталей. Для одной опоры используется окрестность глубиной до двух рёбер. Модель получает пронумерованные факты, а документы-источники берутся из атрибутов переданных рёбер. При неизвестном коде или отсутствии фактов система возвращает отказ без обращения к модели.

В режиме `global` модель даёт частичный ответ по каждой сводке и оценивает его полезность. Полезные частичные ответы объединяются отдельным вызовом, а источники берутся из сообществ, которые дали эти ответы. Режим предназначен для вопросов по нескольким документам, например о частоте отказов в линейке.

### Инструменты агента (FR-6)

В `TOOL_SCHEMAS` для каждого инструмента заданы имя, назначение, типы и список обязательных аргументов. Допустимые склады перечислены в схеме параметра `warehouse`. Функция `build_tools` возвращает словарь, по которому агент сможет найти Python-функцию по её имени.

| Инструмент | Что возвращает |
| --- | --- |
| `search_knowledge` | Ответ локального поиска по графу, факты, источники и признак отказа |
| `summarize_topic` | Ответ по сводкам сообществ, источники и признак отказа |
| `check_stock` | Остаток детали на выбранном складе и признак снятия с производства |
| `get_price` | Цену детали в рублях и признак снятия с производства |
| `create_service_order` | Данные созданного в ERP заказа, включая его номер |

Перед обращением к ERP общий обработчик проверяет формат номера детали и, где это применимо, допустимость склада, положительное целое количество и наличие модели оборудования. Некорректные аргументы, отсутствие данных и отклонение запроса возвращаются как словари с полем `error` и разными сообщениями. Нулевой остаток передаётся как успешный результат. При временной недоступности ERP исключение передаётся вызывающему коду для повторных попыток по FR-8.

В первой версии на эталоне сохранились три связи, и ни одна не совпала с эталоном. Сравнение показывает эффект доработок в совокупности. Вклад изменений промпта и лимита отдельно не измерялся.

Повторная оценка на тех же ответах модели из кеша показала рост полноты связей с 73,9% до 75,8% после исправления повторных дефисов. Точность связей осталась 98,4% при округлении до десятых. Проверки отбросили 59 элементов суммарно по сущностям и связям. По этому числу нельзя определить, сколько обязательных связей пропустила модель и сколько отбросил код. Все семь контрактных тестов извлечения прошли.

### Проверка графа

На кешированных результатах извлечения из 20 фрагментов 16 эталонных документов граф содержал 81 узел и 92 ребра. Встречных замен в этом наборе не было. У ребра от P-1042 к P-1042B вес 1 и источник `bulletin_SB-2025-03.md#0`. Все 13 контрактных тестов извлечения и графа прошли, включая случаи с повтором связи и встречными заменами.

### Полная индексация

На 92 фрагментах полного корпуса получено 120 узлов, 167 рёбер и 18 сообществ. Встречных замен не обнаружено. Извлечение отбросило 207 элементов суммарно по сущностям и связям. Индексация учла 110 запросов к модели, включая 20 ответов из кеша, 77 126 входных и 51 486 выходных токенов. Числа взяты из [artifacts/index_stats.json](artifacts/index_stats.json). Все 13 контрактных тестов сообществ и поиска прошли.

### Оценка поиска по графу

Оценщик засчитал больше ответов у `local`, чем у `global`. Глобальный режим требует 18 запросов к модели для оценки сводок и ещё один, если есть полезные частичные ответы. Среднее за прогон составило 18,667 запроса на вопрос. Оценщик проверяет наличие ключевых фактов в тексте, поэтому результат может расходиться с ручной проверкой окончательного ответа. Так, засчитанный ответ `global` на обзорный вопрос `dev-13` упомянул ожидаемое пусковое реле, но в выводе назвал другой узел и другую линейку. [Оценка local](artifacts/eval_local.json), [оценка global](artifacts/eval_global.json).

## 4. Где граф помогает и где уступает

**`dev-14`, частые отказы в линейке «Гольфстрим».** Плоский RAG сообщил, что ответ в базе знаний не найден. Локальный поиск использовал связи `GS-520 → BELONGS_TO → Гольфстрим` и `GS-520 → FAILED → циркуляционный насос` и назвал циркуляционный насос, который указан в эталоне.

**`dev-01`, регламент по ошибке E-17.** Плоский RAG назвал SP-104, а локальный режим вернул отказ. Граф не сохранил прямую связь ошибки с регламентом, хотя исходный документ был доступен в корпусе.

## 5. Ошибки

**Первая версия FR-1, направление связей.** В ответах по полному корпусу обнаружено 234 связи с переставленными местами типами начала и конца. Например, модель записала `Component → INDICATES → ErrorCode`, тогда как схема требует `ErrorCode → INDICATES → Component`. Проверка типов отбросила такие связи. В бюллетене SB-2025-03 модель записала замену как `P-1042B → REPLACED_BY → P-1042`. Оба конца имеют тип `Part`, поэтому ошибочное направление прошло проверку. В доработанной версии в граф попала замена от P-1042 к P-1042B.

**Первая версия FR-1, обрезанный ответ.** Девять из 92 ответов остановились на лимите 1024 токенов и содержали незавершённый JSON. Среди них был фрагмент с таблицей комплектации `manual_AR-210.md#0`. Повтор отправлял тот же запрос, клиент возвращал тот же ответ из кеша, а функция в итоге пропускала фрагмент целиком.

**Извлечение, вопрос `dev-06`.** Ожидалась деталь P-1042B. Локальный поиск по полному индексу назвал пусковое реле, но не указал номер детали. При разборе таблицы в `manual_AR-210.md#0` модель вернула `HAS_PART` с целью типа `Component`. Схема требует цель типа `Part`, поэтому связь была отброшена. Ребро замены `P-1042 → P-1042B` присутствует в графе, но без `AR-210 → HAS_PART → P-1042` поиск между AR-210 и E-17 не вышел на эту цепочку.

**Контекст поиска, вопрос `dev-13` в режиме `local`.** В контекст попали связи `FAILED` без весов. Модель посчитала строки и получила ничью между пусковым реле и датчиком температуры. Оценщик засчитал ответ по упоминанию пускового реле, хотя оно не было выделено как самый частый отказ.

**Генерация, вопрос `dev-13` в режиме `global`.** Ожидалось пусковое реле в линейке «Арктика». В сводке сообщества было указано пять отказов этого узла, но итоговый ответ выбрал вентилятор испарителя из «Бриза». При объединении частичных ответов модель сравнила числа из разных линеек и вышла за рамки вопроса.

## 7. Следующий шаг

Проверить, помогает ли отдельный пример извлечения из таблицы комплектации правильно различать номер детали и название узла. Для этого нужно добавить в запрос пример связи `HAS_PART`, повторно построить индекс и сравнить полноту связей, ответ на `dev-06` и долю верных ответов на вопросах `multihop` с текущим прогоном.

## 10. Исправление ошибки извлечения после контрольного прогона

Контрольный прогон выявил, что часть ответов FR-1 обрезалась на стандартном лимите 1024 токенов.
Повторная попытка отправляла тот же набор сообщений, поэтому файловый кеш LLM возвращал тот же
незавершённый JSON. В результате длинный фрагмент руководства, включая таблицу комплектации
AR-210, мог целиком выпасть из графа.

В исправленной реализации лимит ответа увеличен до 2048 токенов. При повторе к истории добавляется
отдельная инструкция вернуть полный JSON, поэтому повторный запрос получает другой ключ кеша.
Структура ответа проверяется моделями Pydantic. В системный запрос передаётся закрытый словарь
названий и два явных примера: связь `ErrorCode → INDICATES → Component` и разбор строки
комплектации в цепочку `Model → HAS_PART → Part → IS_A → Component` с поставщиком детали.

Дополнительно исправляется повторный дефис в кодах, например `P--1042` приводится к `P-1042`
до общей канонизации. Направление `REPLACED_BY` явно описано как «старая деталь → новая» и
показано в инструкции модели. Программная проверка по-прежнему требует соответствия типов схеме,
наличия кодов в исходном чанке и канонического словарного имени.

После изменений все 13 контрактных тестов FR-1 и FR-2 проходят. Отдельная проверка обрезанного
первого ответа подтвердила два разных запроса с лимитом 2048, нормализацию `P--1042` и получение
связи `P-1042 → REPLACED_BY → P-1042B`. Старые метрики в таблицах выше сохранены без изменений:
для обновления чисел требуется очистить или отделить старый кеш, повторно выполнить
`make eval-extraction`, пересобрать индекс командой `make index` и заново запустить оценки
`local` и `global`.

## 11. Результаты повторной оценки и индексации

После исправления FR-1 повторно выполнены команды `eval-extraction` и `index` с моделью
`qwen3:4b-instruct-2507-q4_K_M`. Оценка на 16 эталонных документах показала Precision 100%
и Recall 82,6% для связей: найдено 135 допустимых связей при 161 обязательной связи в эталоне.
Для сущностей получены Precision 96,5% и Recall 98,8%: найдено 173 сущности при 165 обязательных
сущностях в эталоне. Программные проверки FR-1 отбросили 33 неподтверждённых элемента.

Полная индексация обработала 92 фрагмента корпуса. Итоговый граф содержит 122 узла и 180 рёбер,
алгоритм Louvain выделил 18 сообществ. При объединении графа конфликтов не обнаружено, проверки
извлечения отбросили 197 элементов. Индексация учла 110 логических обращений к модели:
92 извлечения из фрагментов и 18 сводок сообществ. Все 110 результатов были получены из файлового
кеша; сохранённая статистика ответов составляет 101 467 входных и 48 341 выходной токен.

Новый результат показывает выбранный компромисс FR-1: строгая проверка практически исключает
ложные связи, но часть обязательных отношений остаётся пропущенной. По сравнению с предыдущим
контрольным прогоном полнота связей выросла с 75,8% до 82,6%, а их точность — с 98,4% до 100%.
Актуальные числа сохранены в `artifacts/eval_extraction.json` и `artifacts/index_stats.json`.
